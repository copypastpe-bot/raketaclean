# ТЗ: админ проводит уборку клининга

Дата: 2026-10-30. Решения владельца — в разговоре 30.10, перечислены ниже.
Бот: рабочий (корень репозитория). Перед работой прочитать `CLAUDE.md` корня,
`cleaning/handlers.py.map.md`, нужные участки `bot.py.map.md`.

Базовый коммит: SHA из промпта.

## Зачем

Проводить уборку (`/cleaning_order`, «🧹 Провести уборку») сейчас может только бригадир
клининга. Проверка `can_create_cleaning_order` (`cleaning/access.py:50`) требует право
`cleaning_create_orders` **и** запись в `cleaning_foremen`. Право у ролей `admin` и
`superadmin` уже есть (`ROLE_MATRIX`, `bot.py` ~5191), записи в `cleaning_foremen` у них нет,
поэтому админ получает «Команда доступна только клининг-бригадирам.». В подменю админа
«Клининг» (`admin_cleaning_kb`, `bot.py` ~5662) кнопки проведения уборки нет.

`do_provesti` (`cleaning/handlers.py:729`) берёт бригадира по `tg_user_id` и пишет его id в
`cleaning_orders.foreman_id` (обязательное поле, ссылка на `cleaning_foremen`,
`app/migrations/0006_cleaning.sql`). Наличные и карта идут в `cash_holder='olya'`
(`_income_cash_holder`), «Расчётный» — в `'dima'`, расходы уборки — всегда `'olya'`.

Факты базы (чтение 30.10): активных записей `cleaning_foremen` две — id 1 «Тест» и id 2
«Ольга», обе с ролью `cleaner` в `staff`; все 15 уборок проведены на id 2. У `staff` есть
`first_name`, `last_name`, `full_name`.

## Решения владельца (30.10)

1. Роли `admin` и `superadmin` проводят уборку тем же сценарием, что и Оля.
2. Админу после расходов задаётся один вопрос «Оля / Дима». Ответ решает три вещи сразу:
   - куда идут наличные и карта: «Оля» → `olya`, «Дима» → `dima`;
   - откуда расходы этой уборки: «Оля» → `olya`, «Дима» → `dima`;
   - чья уборка (`foreman_id`, строка «Бригадир:» в отчёте): «Оля» → запись Ольги,
     «Дима» → запись самого админа.
3. «Расчётный» при любом ответе — `dima`, как сейчас.
4. Сценарий Оли (роль `cleaner`) не меняется ни в чём: без вопроса, всё в `olya`, её запись.
5. Без выключателя.
6. Ожидание оплаты по счёту в клининге — **не делать**.

Решения координатора (владелец утвердил план 30.10):

- Вход админа: кнопка «Провести уборку» в подменю «Клининг» и команда `/cleaning_order`.
- Какая запись `cleaning_foremen` — «Оля», задаёт настройка `CLEANING_OLYA_FOREMAN_ID`
  (на сервере значение `2`). Искать по имени нельзя: рядом активная запись «Тест».
- Запись админа: при первом ответе «Дима» бот сам заводит админу строку в `cleaning_foremen`
  (`tg_user_id` админа, имя из `staff`). Структура базы не меняется, миграций нет.
- Новых тестов не писать; существующие, которые ломает новая кнопка, привести в соответствие.

## Задача 1. Доступ и ветка админа

1. Какой путь у человека — решает роль, а не запись в `cleaning_foremen`: роль `admin` или
   `superadmin` (`is_cleaning_admin`) → путь админа; иначе → прежний путь бригадира
   (`can_create_cleaning_order`, без изменений). Админ после первой уборки «Дима» получит
   запись в `cleaning_foremen`, и это не должно перевести его на путь Оли.
2. `start_cleaning_order`: пускать путь админа при праве `cleaning_create_orders`; отказ
   остальным — прежним текстом. В состояние сценария положить признак пути админа.
3. Найти все места сценария `CleaningOrderFSM`, где решение зависит от того, кто проводит,
   и поправить по пунктам 1–2. `do_provesti` перепроверяет доступ на «Провести»: путь админа —
   роль всё ещё `admin`/`superadmin`, иначе «Доступ отозван.», как сейчас у бригадира.

## Задача 2. Шаг «Оля / Дима»

1. Новое состояние `CleaningOrderFSM.cash_holder` (`cleaning/fsm.py`).
2. Путь админа: «Готово» на шаге расходов (`got_expense_category`) ведёт на этот шаг, а не
   сразу в сводку. Путь Оли — сразу в сводку, как сейчас.
3. Вопрос: «Чья уборка? «Оля» — деньги и расходы в «Деньги Ольга», бригадир Ольга. «Дима» —
   в «Касса (Дима)», бригадир — вы.» Кнопки — `_cash_holder_kb()`, разбор —
   `_parse_cash_holder`, непонятный ответ — `_reask_cash_holder`.
4. Ответ «Оля»: прочитать `CLEANING_OLYA_FOREMAN_ID` из окружения (как
   `get_min_order_amount` в `cleaning/orders.py`). Пусто, не целое число, нет такой
   активной записи в `cleaning_foremen` → ответ «Запись Оли не настроена
   (CLEANING_OLYA_FOREMAN_ID). Выберите «Дима» или «Отмена».», остаться на шаге. Значение
   разбирать строго целым: systemd не срезает хвостовой комментарий в строке файла.
5. Ответ сохранить в состояние; дальше — `_show_confirm`.
6. В сводке пути админа две строки после «Оплата/Расходы»:
   «Деньги и расходы: Деньги Ольга» или «Деньги и расходы: Касса (Дима)» (подписи —
   `CASH_HOLDER_OLYA_LABEL` / `CASH_HOLDER_DIMA_LABEL`) и «Бригадир: <имя>». Сводка Оли
   не меняется.
7. «Отмена»/«Отменить» на новом шаге работает (обработчик `cancel` ловит группу
   `CleaningOrderFSM` — проверить).

## Задача 3. Проведение по ответу

В `do_provesti`, путь админа:

1. Бригадир уборки: «Оля» → запись по `CLEANING_OLYA_FOREMAN_ID` (перечитать, нет/неактивна →
   ответ из задачи 2 п.4, сценарий не закрывать, ничего не записано). «Дима» → запись админа
   по его `tg_user_id`; нет — завести в той же транзакции: `fn`/`ln` из `staff.first_name` /
   `staff.last_name`, пусто — из `staff.full_name`, пусто — из имени Telegram; `fn`
   обязательно непустое. Учесть `UNIQUE (tg_user_id)`.
2. Приход: «Наличные»/«Карта» → выбранная кучка; «Расчётный» → `dima` всегда; сертификат —
   как сейчас (в кассу не идёт).
3. Расходы уборки → выбранная кучка.
4. Признак «уборка задела деньги Оли» (`touches_olya`) считать по фактическим строкам:
   есть приход или расход в `olya`. От него зависит строка «Деньги Ольга» в отчёте.
5. Имя в отчёте (`foreman_name`) — из выбранной записи.
6. Все ответы `do_provesti` админу в конце («проведён», «уже проведён ранее», отказы,
   закрывающие сценарий) — с его главным меню через `_after_op_kb`; Оле — как сейчас.
7. Путь Оли — построчно без изменений.
