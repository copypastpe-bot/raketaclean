# Ревью блока работ по адресам — замечания

Дата: 2026-09-17
Ревьюер: reviewer (Sonnet), ревью качества на весь блок (химчистка 16.09 + клининг 17.09)
Проверил координатор: замечание 1 воспроизведено на живом Postgres.

## В работу

### 1. Отчёты по заказам химчистки не уйдут никогда — сломан INSERT в очередь

`bot.py:7938`, функция `_enqueue_order_report`:

```sql
INSERT INTO pending_order_reports (order_id, payload)
VALUES ($1, $2::jsonb)
ON CONFLICT (order_id) DO NOTHING
```

После миграции `0011` первичный ключ таблицы составной — `(kind, order_id)`, отдельного
уникального ограничения на `order_id` больше нет. Postgres на такой запрос отвечает
`there is no unique or exclusion constraint matching the ON CONFLICT specification`.

**Воспроизведено координатором на живом Postgres 17.09** — не гипотеза. Тот же запрос
у уборок (`cleaning/handlers.py:596`) написан верно: `(kind, order_id)` и с указанием `kind`.

Исключение гасится в `try/except` (`bot.py:14759`, `logging.warning`), поэтому заказ
проводится, деньги в кассу пишутся — а строка в очередь **не попадает никогда**. Следствия:

- отчёт в `ORDERS_CONFIRM_CHAT_ID` по заказам химчистки не уходит вообще;
- сообщение в «Ракета деньги» по ним не уходит;
- оба сигнала в `LOGS_CHAT_ID` для химчистки не сработают: они читаются из строк очереди.

То есть задачи 5 и 6 ТЗ от 16.09 после сегодняшней миграции не работают для основного
контура. Контур уборок не задет.

**Починить:** привести запрос к виду уборок — указывать `kind` явно и конфликтовать
по паре `(kind, order_id)`.

### 2. Тесты этого не ловят и не могли поймать

`tests/test_pending_order_reports.py`, `EnqueueOrderReportTests` работает через `FakeConn`,
чей `execute()` только записывает вызов и возвращает `"UPDATE 1"`. В тестах рабочего бота
**живой базы нет вовсе** — `TEST_DB_DSN`, `asyncpg.connect` и `create_pool` не встречаются
ни в одном файле `tests/`. Поэтому 344 зелёных теста и дефект выше существуют одновременно.

**Починить:** тест, который ловит именно это — расхождение SQL-запроса с реальной схемой.
Способ на усмотрение исполнителя: либо проверка запросов против настоящего Postgres (как
устроено в админ-боте через `TEST_DB_DSN`), либо более дешёвый приём, если он честно ловит
несовпадение `ON CONFLICT` со схемой. Заглушка, повторяющая ошибку задним числом, не годится.

## На потом (решает владелец)

### 3. `ensure_pending_order_reports_schema` не мигрирует уже существующую таблицу

`bot.py:3533`. `CREATE TABLE IF NOT EXISTS` со составным ключом сработает только на пустой
базе; для таблицы, созданной ранее по миграции `0009` (одиночный ключ), код добавит колонку
`kind`, но старый ключ и ссылку не тронет — в отличие от миграции `0011`, которая их снимает.

Для первого боевого выката не выстрелит: в проде таблицы ещё нет, работа от 16.09
не разворачивалась. Риск — на стендах и тестовых базах, где таблица уже создавалась.

### 4. `fetch_lead_address` не отличает «сделку удалили» от «адрес пуст»

`raketa-admin-bot/adminbot/amo/fields.py:49` → `client.get_lead` возвращает `None` и на 404,
и на пустое поле. Сетевой сбой отработан верно (исключение, счётчик не тратится), а вот
удалённая сделка ведёт себя как «адрес пуст»: робот пришлёт все 7 напоминаний и замолчит
по потолку. Не авария, крайний случай.

## Проверено, замечаний нет

Фоновое дозаполнение адреса (не перезаписывает заполненное, сбой одной строки не стопорит
остальные, одинаково обслуживает оба контура); запись `deal_address` в связку, включая путь
`already_done` и уборки; цикл напоминаний с перепроверкой CRM, потолком и мутом; диалог
бригадира после правок (осиротевших состояний нет, цепочка верна для нового и известного
клиента); печать пустого адреса и комментария («None» не появится); один из восьми вызовов
`send_cleaning_money_flow` подвинут, семь не тронуты; `cleaning/schema.py` соответствует
миграции `0010`; команды `GRANT` записаны в оба runbook; персональные данные в журналы
не попадают.
