# ТЗ: автозвонок — кнопка «Я уже перезвонил» и проверка истории АТС перед повтором

Дата: 2026-10-23. Решения владельца — в разговоре 23.10, перечислены ниже.
Два бота: рабочий (корень репозитория) и админ-бот (`raketa-admin-bot/`). Перед работой
прочитать `CLAUDE.md` корня и `raketa-admin-bot/CLAUDE.md`.

Базовый коммит: SHA из промпта.

## Зачем

Робот автозвонка (админ-бот, `adminbot/autocall/`) звонит менеджеру на мобильный и соединяет
с клиентом. Не дозвонился — повторяет по таймеру: через 5 минут, если не взял менеджер, через
10 минут, если не взял клиент (`chain.py`, `RETRY_MANAGER`/`RETRY_CLIENT`). Перед повтором
робот ничего не проверяет. Менеджер после пропущенного звонка сам находит клиента и
перезванивает **с мобильного** — а робот через 5–10 минут звонит снова и соединяет их ещё раз.

## Решения владельца (23.10)

1. После каждого недозвона, за которым следует повтор (не взял менеджер **или** не взял
   клиент), менеджеру сразу приходит сообщение с кнопкой **«Я уже перезвонил»**. Ожидание
   прежнее: 5 минут (не взял менеджер), 10 минут (не взял клиент). Предел 4 попытки — прежний.
2. Сообщение — **в личку рабочего бота**, там же, где сообщения о пропущенных звонках.
3. По каждой сделке — **одно сообщение, которое правится**, а не новое на каждую попытку:
   пока впереди повтор — время повтора и кнопка; робот закончил — итог без кнопки.
4. Нажата кнопка → робот останавливается и пишет в сделку примечание
   «Менеджер перезвонил клиенту сам (кнопка), автозвонок остановлен».
5. Перед повтором робот смотрит историю АТС: **любой** звонок клиента на номер компании после
   попытки робота — **даже пропущенный** — отменяет повтор (пропущенные менеджеру и так приходят
   отдельным сообщением).
6. Менеджер звонит с мобильного (сим-карта) — такой звонок АТС не видит; его ловит только кнопка.

Решения координатора (владелец утвердил проект 23.10):

- Два выключателя, **оба выключены**, пока владелец не включит: кнопка и проверка истории АТС.
- Звонок по номеру клиента через АТС из офиса тоже отменяет повтор. Свои звонки робота — нет.
- Владельцу ничего нового не приходит.
- Кнопка нажата, пока робот уже набирает номер, — этот звонок не останавливается (секунды),
  следующего повтора не будет.
- Кнопка нажата, когда робот уже закончил, — рабочий бот отвечает «Робот по этой заявке уже не
  звонит».

Решение координатора при написании ТЗ (вынесено владельцу в ответе вместе с ТЗ):

- Проверка истории АТС не смогла ответить (сеть, ошибка АТС) — робот звонит, как раньше, и
  пишет в журнал `recheck_failed`. Сбой проверки не должен задерживать звонок клиенту.

## Факты (источник — команда или код на `70dec6a`)

- Сообщения менеджеру шлёт админ-бот **ключом рабочего бота**, только на отправку; слушает этот
  диалог рабочий бот (`raketa-admin-bot/adminbot/main.py`, `_make_autocall_manager_sender`,
  настройки `WORKER_TG_TOKEN`, `MANAGER_TG_CHAT_ID`). Значит, нажатие кнопки приходит **рабочему
  боту**, админ-бот его не увидит.
- Рабочий бот принимает нажатия кнопок в личке без проверки ролей: единственная прослойка —
  `IgnoreNonPrivateMiddleware` (`bot.py`, глушит только группы). Образец кнопки —
  `order_close_snooze_cb` (`bot.py`, префикс `ORDER_CLOSE_SNOOZE_CB_PREFIX`).
- Роль `bot` читает `adminbot.autocall_leads` (`has_table_privilege` = t на проде, 23.10).
- Таблицы, которые роль `bot` создаёт в `public`, роль `adminbot` читает автоматически
  (`pg_default_acl`: `bot | public | {adminbot=r/bot}`, прод 23.10). Миграции рабочего бота
  накатываются от роли `bot` (`docs/deploy.md`, «Миграции и их журнал»).
- Админ-бот читает таблицы рабочего бота через `bot_pool` — образец `PgPromoCallbackSource`
  (`adminbot/promo_callback/store.py`).
- У `adminbot.autocall_leads` нет CHECK на `status` (только PK) — новый статус миграции не требует.
- При повторе движок обнуляет `called_at` и `call_id` (`engine.py`, `_process_calling`, ветка
  `Retry`) — время прошлой попытки к моменту повтора уже потеряно; его надо хранить отдельно.
- История АТС: `mongo_history/search.json`, поля формы `start_stamp_from`, `start_stamp_to`,
  `per_page` (`pbx.py`, `call_outcome`). В записи известны `uuid`, `destination_number`,
  `contacted`, `user_talk_time`, `end_stamp`, `hangup_cause`, `events` (`outcome_from_history`).
  **Поле с номером звонящего во входящем звонке и число записей на одну попытку робота —
  не разведаны** (см. Задачу 0).
- При протухшем ключе АТС клиент робота сам получает новый (`OnlinePbx._request`, один повтор).
- Выключатели админ-бота ставит обёртка `sudo raketa-admin-bot-update --<ключ>`
  (`raketa-admin-bot/deploy/update.sh`, разбор ключей — по образцу `--autocall-on`).
  Как обёртка попадает в `/usr/local/bin` и обновляется ли она при выкате — **предположение,
  проверить** при выкате (`ls -l $(command -v raketa-admin-bot-update)`).
- Последние миграции: рабочий бот — `0018`, админ-бот — `021` (`ls`, 23.10).

## Устройство

```
робот не дозвонился ─► сообщение менеджеру (ключ рабочего бота) с кнопкой
                         │ номер сообщения → adminbot.autocall_leads.tg_message_id
менеджер нажал ─► рабочий бот: строка в public.autocall_manager_callbacks,
                  сообщение: «Принято…», кнопка убрана
подошло время повтора ─► админ-бот:
   1) есть строка нажатия по сделке?          → стоп, причина manager_called
   2) в истории АТС звонок с номером клиента
      после прошлой попытки (не свой)?         → стоп, причина client_called
   3) иначе звонит, как раньше
итог цепочки ─► то же сообщение правится на итог без кнопки (+ примечание в сделку)
```

Новый финальный статус цепочки — `cancelled` (в `FINAL_STATUSES`), причина — в журнале
`autocall_actions` (`cancelled`, `{"reason": "manager_called"|"client_called"}`).

Префикс кнопки — `autocall_called:<lead_id>`. Он живёт в двух кодовых базах: константа в
рабочем боте и в админ-боте, в обеих — тест на дословное значение.

### Тексты (предложение координатора; телефон и ссылка — как в нынешнем `manager_text`)

Сообщение с кнопкой (кнопка: `Я уже перезвонил`):

- не взял менеджер: `Робот не дозвонился до вас по заявке. Повтор в 10:12.`
- не взял клиент: `Клиент не взял трубку. Повтор в 10:22.`
- повтор на другой день (окно 10–20): `… Повтор 24.10 в 10:00.`

Дальше строки `Телефон клиента: …` и ссылка на сделку — как сейчас.

Итог (правка того же сообщения, без кнопки):

- нажали кнопку (рабочий бот, сразу): прежний текст + пустая строка +
  `✅ Принято: робот по этой заявке больше не позвонит.`
- остановлен по кнопке (админ-бот, при повторе): `Вы перезвонили клиенту сами — робот остановился.`
- остановлен по истории АТС: `С клиентом уже был звонок через АТС в 10:09 — робот остановился.`
- соединил: `Робот соединил вас с клиентом в 10:12.`
- `no_contact_final`, `manager_unreachable`, `attempts_exhausted` — нынешние тексты.

Примечания в сделку (`notes.py`):

- `manager_called`: `Автозвонок: менеджер перезвонил клиенту сам (кнопка). Робот остановился.`
- `client_called`: `Автозвонок: с клиентом уже был звонок через АТС (10:09 МСК) — клиент перезвонил
  сам или звонили из офиса. Робот остановился.`

## Задачи

### Задача 0. Разведка истории АТС (координатор, до Задачи 3)

Скрипт только читает `mongo_history/search.json` клиентом робота и печатает **без телефонов**
(хвост 4 цифры): ключи записей, где встречается номер клиента, `start_stamp`, `uuid`, признак
направления, если есть. Образцы — три известные попытки робота: сделка 31750907, 22.10 10:00:45
(менеджер не взял) и 10:07:07 (соединил); 31746499, 20.10 15:23:49 (клиент не взял) — плюс любой
входящий звонок клиента за те же дни. Ответить: сколько записей даёт одна попытка робота; в каком
поле номер звонящего у входящего; как отличить свою запись робота от чужой (`uuid`, время).
Ключ АТС не печатается и не вводится руками: скрипт запускает владелец (`! ssh …`) либо
координатор с его разрешения. Итог — в раздел «Разведка» этого ТЗ, до начала Задачи 3.

Выполнено 23.10 координатором (разрешение владельца; ключ из `/home/admin/.pbx.env` не печатался).

#### Разведка (итог Задачи 0)

Источник — вывод скрипта по окнам 22.10 09:59–10:15 и 20.10 15:16–15:40 МСК.

- **Одна попытка робота — одна запись истории.** В ней `destination_number` = телефон клиента,
  `caller_id_number` (и `caller_id_name`) = набранный телефон менеджера из `PBX_MANAGER_DIAL`
  (рабочий в первой попытке, личный после неудачи менеджера), `start_stamp` — unix-время строкой,
  совпадает с `called_at` с точностью до секунд, `uuid` = боевой `call_id`, если он пришёл.
- **`accountcode` = `inbound` у всех записей, в том числе у звонков робота** — направление по нему
  не определить, на него не опираться.
- **Входящий от клиента** (20.10 15:24:55, сделка 31746499, через 30 с после неудачной попытки
  робота): `caller_id_number` = телефон клиента, `destination_number` = номер, с которого ему звонил
  робот; события — `transfer` на внутренние `5100`, `5000`, `100` и `user` `100`; пропущенный:
  `contacted` = false, `user_talk_time` = 0, `hangup_cause` = `NORMAL_CLEARING`.
- В окне бывают записи, где номер клиента не встречается ни в одном поле, — к делу не относятся.
- Номера в истории — в разных форматах; сравнивать по последним 10 цифрам (как `_matches_phone`).

**Правило для Задачи 3 (решение координатора по итогам разведки):**

- запись «с клиентом» — последние 10 цифр `caller_id_number` **или** `destination_number` равны
  телефону клиента;
- своя запись робота — `destination_number` = клиент **и** `caller_id_number` — один из телефонов
  менеджера (`manager_dials` движка, по 10 цифрам) **и** `start_stamp` не дальше 60 с от
  `last_called_at`; такая запись не считается. Звонок с номера менеджера через АТС позже этих 60 с
  считается (это уже не попытка робота);
- окно запроса — `start_stamp_from` = `last_called_at`, `start_stamp_to` = now; ответ — самый ранний
  `start_stamp` среди записей «с клиентом», кроме своей; нет таких — `None`.

**Решение 5 подтверждено владельцем 23.10 после живого случая.** 20.10 (сделка 31746499) клиент сам
перезвонил в 15:24 и не дозвонился, робот в 15:35 позвонил снова и соединил. По правилу этот повтор
будет отменён — владелец решил так оставить: пропущенный ловит менеджер по своему сообщению.
