# ТЗ — цепочка заказа: календарь → CRM → мастер → оплата

Дата: 2026-09-22
Заказчик: владелец (Евгений)
Основание: бриф `docs/plans/2026-09-18-brief-notifications-backlog.md`, задачи 8, 9, 12–18;
разбор и решения владельца 22.09 (эта сессия). Закрывает задачи 8, 9, 12, 13, 14, 15, 16, 18 брифа.
Затрагивает: админ-бот (`raketa-admin-bot/`) и рабочий бот (корень репозитория, `bot.py`).

## Зачем

Робот ведёт заказ как две несвязанные карточки: запись календаря и заказ мастера. Каждая
сама ищет сделку в CRM по телефону клиента. Пока у клиента одна открытая сделка, это
работает. Две и больше в один день (случай Натальи, 20–22.09): робот забирает чужую
автосделку, задаёт владельцу вопрос с тремя одинаковыми кнопками, а неверный ответ
кладёт неверный адрес в три места базы рабочего бота.

После работы заказ живёт одной цепочкой «запись календаря → лид воронки 1 → сделка
воронки 2 → заказ мастера → оплата». Каждое звено робот знает точно, а не угадывает:
дочку берёт по служебному примечанию сейлзбота, заказ мастера получает номер сделки
ещё до проведения, оплата по счёту доводит сделку до конца сама.

## Бизнес-процесс (слова владельца 22.09)

Контур календаря:

1. Менеджер завёл заказ в календарь → робот создал лид в воронке 1 (первичной), сейлзбот
   создал сделку в воронке 2 (реализации). В сделках: адрес, клиент, дата, комментарий.
2. Менеджер изменил запись → робот меняет сначала лид воронки 1, потом дочку в воронке 2.
3. Менеджер удалил запись → владелец получил вопрос и нажал «Закрыть сделку» → робот
   закрывает сделку воронки 2 с комментарием «заказ отменён» и датой; воронку 1 не трогает.
4. Тот же вопрос, нажато «Разберусь сам» → робот помечает сделку как переданную
   владельцу и больше не трогает (работает уже сегодня).
5. Несколько записей на один день на один контакт → по каждой своя цепочка.

Контур мастера:

1. Мастер провёл заказ в боте → робот находит сделку воронки 2, заполняет суммы, мастера,
   оплату и проводит в «выполнено и оплата получена».
2. Заказ по счёту → робот проводит в «Заказ выполнен». Когда админ привязал оплату к
   заказу, робот ставит сумму, переводит в «выполнено и оплата получена», закрывает
   задачу «получить оплату».
3. Несколько заказов одного клиента в день на разных адресах → мастер сам выбирает
   адрес при проведении, вопрос владельцу не нужен.

## Решения владельца 22.09

1. Первым делаем робота и его поведение; логику лечим глобально, заплатки не лепим.
2. Дочка берётся по примечанию сейлзбота, а не «первая свободная». Во всех трёх контурах.
3. Таблица для мастера содержит только заказы, заведённые календарём: календарь —
   первичный источник заказов.
4. Вход мастера — **вариант 2**: в нынешнем «🧾 Заказ» после телефона, если записей на
   день две и больше, мастер выбирает адрес. Кнопка «Заказы сегодня» не делается.
5. Удаление записи: воронку 1 не трогаем; сделку воронки 2 закрываем с комментарием
   «заказ отменён» и датой.
6. Чужой номер / смена номера в записи: робот **не блокирует и не переносит**. Сверяет пару
   «номер + имя» записи с контактом сделки; расходится → уведомление в личку со ссылкой на
   сделку и кнопкой «я разобрался», раз в сутки, потолок 7 дней. Механика напоминаний про адрес.
7. Оплата по счёту: робот сам доводит сделку. Пять оплаченных заказов при первом запуске
   провести по цепочке и прислать отчёт. Перед выкатом пересчитать ждущих по базе.
8. Уборки — потом, отдельным шагом. Владелец за ними последит.
9. Кнопки выбора сделки сделать понятными: адреса и ссылки текстом, номера на кнопках.

## Принято координатором (владелец не отменил)

- Одна запись на день → заказ привязывается молча, мастера не спрашиваем.
- Окно по дате для мастера: сегодня и вчера по Москве.
- В списке всегда кнопка «Не из списка» → старый путь через матчер.
- Телефон ищется по всем номерам записи, не только по первому.
- Дата в комментарии закрытия — дата заказа из записи. Причина закрытия «Пропала
  потребность», если владелец не поставил свою (как сейчас).
- Перед каждым напоминанием про контакт робот перечитывает контакт в CRM и замолкает сам,
  если уже сходится.
- Сделка по счёту, вопреки ожиданию оказавшаяся на финальной стадии: стадию не трогаем,
  сумму правим только с заглушки (< 100 ₽).
- Адрес заказа при смене привязки не переписываем (задача 17 брифа закрывается как
  «редкий случай»).
- Отчёт по коврам (задача 10 брифа) не входит; в коврах чинятся только дочка и таймер.
- Каждый новый кусок под своим выключателем, по умолчанию выключен.
- Окно для рабочего бота — представление в схеме `adminbot`, не отдельная таблица.

## Задача 1. Дочка по примечанию сейлзбота

**Три шага ожидания** — найди все `_step_wait_salesbot` (календарь, заказы, ковры) и

## Задача 11. Робот доводит сделку после поступления денег

**Связка** (`017_wire_payment.sql`): `adminbot.amo_links` + `payment_pending boolean`,
`payment_synced_at timestamptz`. В `sync/engine.py` там, где `_final_stage` даёт «Заказ
выполнен» из-за ожидания оплаты (`_payment_pending`), ставить `payment_pending = true`.

**Источник работы** (`sync/watcher.py`, `db.py`): запрос «оплата пришла, в CRM не
доведено»: заказы с `created_at >= backlog_from`, способ оплаты безнал
(`lower(replace(payment_method,'ё','е')) in ('р/с','расчетный')` — так же, как `WIRE_METHODS`),
`awaiting_wire_payment = false`, связка `done`, `payment_synced_at IS NULL`,
`COALESCE(payment_pending, true)` — `NULL` у пяти исторических заказов, для них решает
стадия сделки.

**Обработка** (`Engine.process_payment(order, link)`): прочитать дочку.
- Стадия «Заказ выполнен» (`REAL_STAGE_DONE`) → `update_lead(price=order.amount_total)`,
  `move_lead` в `STATUS_SUCCESS`, закрыть открытые задачи сделки (тот же способ, что
  `_step_close_autotasks`), примечание `🤖 Оплата по счёту получена: N ₽. Сделка проведена
  в «выполнено и оплата получена».`
- Стадия финальная → стадию не трогать; `price < 100` → поставить сумму и примечание
  «сумма уточнена по оплате»; иначе ничего.
- В обоих случаях `payment_synced_at = now()`, действие `wire_payment_synced` в журнал.
- Отчёт владельцу через `OwnerMail`, свой вид письма: `💸 Заказ №588 · Имя · <телефон>
  · 5 500 ₽ по счёту · сделка #… → «выполнено и оплата получена», закрыто задач: N ·
  <ссылка>`. В репетиции — с пометкой `mark_rehearsal`.

**Выключатели:** `WIRE_PAYMENT_ENABLED` (выкл.) и `WIRE_PAYMENT_DRY_RUN` (вкл.), ключи
`--wire-payment-on/off/live/rehearsal`. Свой `dry_run`, а не общий `AMO_SYNC_DRY_RUN`:
проведение заказов уже в бою, ронять его в репетицию ради этого нельзя.

**Тесты:** заказ по счёту → связка получила `payment_pending`; снят признак → одна
обработка, второй раз не берётся; сделка уже финальная с 1 ₽ → только сумма; с нормальной
суммой → ничего, но `payment_synced_at` стоит; репетиция → в амо ноль записей, отчёт с пометкой.
