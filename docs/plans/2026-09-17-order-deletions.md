# ТЗ: удаление заказа освобождает сделку в amoCRM

дата: 2026-09-17
автор: координатор (Opus), решения владельца по ходу разбора
статус: к исполнению

## Зачем

Мастер провёл заказ, робот оформил сделку в CRM. Потом выяснилось, что заказ
проведён неверно — владелец удаляет его в рабочем боте. Сегодня на этом всё
останавливается: заказ исчезает из базы, а память робота о нём живёт. Из-за
этого сделка в CRM остаётся закрытой как успешная, хотя работы не было, и тот же
клиент при повторном проведении получает в CRM вторую сделку.

Нужно: удалили заказ — робот отвязывает сделку, возвращает её на этап
«Заказ подтвержден», оставляет в сделке примечание и пишет владельцу.
Если мастер проведёт заказ заново, робот подхватит ту же сделку и доведёт её
штатно. Если не проведёт — владелец увидит открытую сделку и сообщение и
разберётся сам.

## Факты (проверены 17.09.2026, источник указан)

1. Химчистка и уборки удаляются по-разному:
   - заказ химчистки удаляется физически: `DELETE FROM orders` (`bot.py:12183`,
     обработчик `order_remove_confirm` с `bot.py:12076`), следов не остаётся;
   - уборка помечается удалённой: `UPDATE cleaning_orders SET deleted_at`
     (`cleaning/admin_ops.py:96`), строка остаётся.
2. Номера заказов не переиспользуются: `orders.id` и `cleaning_orders.id`
   выдаёт счётчик Postgres (`nextval('orders_id_seq')`), на проде последний
   выданный 638 = максимальный заказ 638. Удаление счётчик не отматывает,
   поэтому номер удалённого заказа — надёжный ключ.
3. Обе схемы живут в одной базе: `ADMINBOT_DB_DSN` по умолчанию равен
   `BOT_DB_DSN` (`raketa-admin-bot/adminbot/config.py:281`). JOIN между
   `public` и `adminbot` в одном запросе допустим — проверить фактически.
4. Роль `adminbot` получает SELECT на новые таблицы `public` автоматически:
   на проде стоит `ALTER DEFAULT PRIVILEGES` для роли `bot`
   (`pg_default_acl` → `{adminbot=r/bot}`), и свежая таблица
   `pending_order_reports` (создана 17.09) уже имеет `adminbot=r/bot`.
   **Условие: миграцию применяет роль `bot`.** Применение от `postgres`
   прав не даст.
5. Робот работает одним проходом раз в 60 секунд
   (`config.py:189`, `poll_interval_sec`), заказы внутри прохода идут по
   одному по возрастанию номера (`sync/watcher.py:186`). Параллельной
   обработки двух заказов нет.
6. Связку робот заводит в момент, когда впервые увидел заказ
   (`sync/engine.py:110`), ещё до похода в CRM.
7. Матчер выбрасывает из кандидатов занятые сделки (`sync/matcher.py:310`)
   и сделки в финальных статусах (`is_open`, `sync/matcher.py:81`).
   Возврат на этап «Заказ подтвержден, Мастер назначен»
   (`adminbot/amo/ids.py:44`, `REAL_STAGE_CONFIRMED = 41463838`) снова делает
   сделку кандидатом.
8. Сделка опознаётся не по номеру заказа (в CRM его нет отдельным полем —
   только в тексте примечания, `sync/engine.py:243-255`), а по телефону плюс
   правила отбора. Сделка, которую робот уже проводил, имеет заполненное поле
   «Дата и время заказа», поэтому при повторном проведении того же заказа
   опознаётся по совпадению дня работы независимо от возраста
   (`sync/matcher.py:127-140`).
9. Инструменты в CRM готовы: `move_lead` и `add_note`
   (`adminbot/amo/client.py:349, 401`).
10. Сообщения владельцу идут через `OwnerMail` с гарантией доставки
    (`adminbot/tg/outbox.py`, таблица `adminbot.owner_outbox`).
11. API amoCRM сделки не удаляет: удалённая сделка возвращается пустым
    объектом без `id` (известное ограничение, `AGENT_STATE.md`).

## Решения владельца (17.09)

1. Связку не удалять, а помечать: «через год опять упрёмся в то, что сейчас
   обходим».
2. Бюджет сделки и поля при откате оставить как есть — перезапишутся при
   повторном проведении.
3. Сделки в CRM не нашли — сообщить владельцу и убрать связку.
4. Разбор удалений — первым шагом того же прохода, без отдельного таймера.
5. Сделка уже закреплена за живым заказом — статус не трогать.
6. Статус откатывать только у закрытой сделки; открытую не трогать.
7. Робот не успел взять удалённый заказ в работу (связки нет) — молчим.
8. Переоформление от пропажи **не различаем**: всегда «Заказ подтвержден»
   плюс сообщение владельцу. Дубль в CRM владелец разбирает руками —
   случаев порядка пяти в год, и он хочет их видеть.

## Задачи

### Задача 1. Рабочий бот: регистр удалений (миграция)

Файл `app/migrations/0012_deleted_orders.sql`, таблица `public.deleted_orders`:

- `order_id` bigint PRIMARY KEY — номер удалённого заказа (номера уникальны
  навсегда, факт 2);
- `phone_digits` text — телефон клиента в том же виде, что в `orders`;
- `client_id` bigint;
- `amount_total` numeric(12,2);
- `deleted_at` timestamptz NOT NULL DEFAULT now();
- `deleted_by` bigint — Telegram-id того, кто удалил.

Индекс по `deleted_at`. Комментарий в шапке файла — зачем таблица нужна,
по образцу соседних миграций.

Приёмка: миграция применена ролью `bot`; `SELECT` из-под роли `adminbot`
проходит (факт 4).

**Выполнено.** Файл `app/migrations/0012_deleted_orders.sql` создан и
проверен локально: `psql` на `raketaclean_test` применяет его без ошибок,
структура таблицы и индекс соответствуют ТЗ. Проверку под ролями `bot` и
`adminbot` делает владелец на проде при выкладке (эти роли существуют
только там).

### Задача 2. Рабочий бот: писать в регистр при удалении заказа

Место: обработчик `order_remove_confirm` (`bot.py:12076`), **внутри той же
транзакции**, рядом с `DELETE FROM orders` (`bot.py:12183`). Если удаление
откатится, регистр не должен соврать.

Данные берутся из уже прочитанной строки заказа (`client_phone`, `client_id`,
`amount_total`) и из события (`query.from_user.id`). Телефон нормализовать той
же функцией, которой пользуется остальной бот — найди её фактическое имя в
`bot.py`, не подставляй по памяти. `ON CONFLICT (order_id) DO NOTHING`.

Уборок это не касается: у них есть `deleted_at` (факт 1).

Приёмка: тест на живом Postgres — удаление заказа кладёт строку в регистр;
откат транзакции строки не оставляет.

### Задача 3. Админ-бот: таблица отметок (миграция 014)

`adminbot.order_deletions_seen`:

- `kind` text NOT NULL — `order` или `cleaning`;
- `order_id` bigint NOT NULL;
- `processed_at` timestamptz NOT NULL DEFAULT now();
- `outcome` text — что сделали (для разбора потом);
- PRIMARY KEY (`kind`, `order_id`).

Почему своя таблица: админ-бот не имеет права писать в `public`, поэтому
отметку о разборе держит у себя. Почему составной ключ: номера заказов и
уборок пересекаются — тот же урок, что в `pending_order_reports`
(миграция `0011` рабочего бота, дефект найден ревью 17.09).

### Задача 4. Админ-бот: источник записей об удалении

Новый модуль (например `adminbot/sync/deletions.py`). Два запроса, оба
возвращают записи, которые ещё не разобраны:

- заказы: `public.deleted_orders` минус `adminbot.order_deletions_seen`
  (`kind='order'`);
- уборки: `public.cleaning_orders` с непустым `deleted_at` минус отметки
  (`kind='cleaning'`).

Оба пула смотрят в одну базу (факт 3) — проверь это фактически в своей среде
до того, как напишешь JOIN между схемами.

### Задача 5. Админ-бот: обработчик удаления

На каждую неразобранную запись, строго в этом порядке:

1. Связки нет → отметить разобранной, владельцу **не писать** (решение 7).
2. Связка есть, но её сделка уже закреплена за связкой другого живого
   заказа → статус **не трогать**; примечание в сделку о том, что заказ №N
   удалён, а сделка осталась за заказом №M; отметить; сообщить владельцу
   (решение 5).
3. Сделки в CRM нет (ответ без `id`, факт 11) → пометить связку, отметить,
   сообщить владельцу «сделки нет, связку убрал» (решение 3).
4. Сделка открыта (статус не финальный) → статус **не трогать**, примечание,
   пометить связку, сообщить (решение 6).
5. Сделка закрыта → вернуть на этап «Заказ подтвержден, Мастер назначен»
   (`move_lead`, факт 7), примечание, пометить связку, сообщить.

Примечание в сделку: что заказ №N удалён из бота такого-то числа во столько-то
по Москве, что сделка возвращена на этап «Заказ подтвержден», что бюджет и
поля оставлены как есть (решение 2).

Пометка связки: статус `cancelled` (не удалять, решение 1) плюс заглушить
напоминания про адрес по этой связке, иначе они всплывут.

Репетицию уважать: в `dry_run` в CRM не писать, решение записывать в журнал
действий, как это делает движок.

Сообщение владельцу — через `OwnerMail` (факт 10), своим видом письма.
Полный телефон и дата работы в сообщении допустимы: бот приватный
(правило проекта про `adminbot.phone.for_owner`).

### Задача 6. Админ-бот: страховка от сирот

Событие может не дойти: служба стояла, запись потерялась, порядок действий
мастера был обратным. Поэтому связка, у которой заказа больше нет, не должна
считаться действующей:

- `fetch_taken_lead_ids` (`adminbot/db.py:372`) — мёртвая связка не держит
  сделку занятой;
- выборка напоминаний про адрес — по мёртвой связке карточки не шлются.

**Найди все** места, где связка считается действующей (включая
`fetch_link_ids_by_status`), и реши по каждому явно; список выше — не полный
перечень, а начало поиска.

Для уборок «мёртвая» означает непустой `deleted_at`, для химчистки —
отсутствие строки заказа.

### Задача 7. Выключатель и runbook

Своя настройка, по умолчанию **выключено** (правило проекта: у каждой функции
свой выключатель). Ключи включения и выключения в
`raketa-admin-bot/deploy/update.sh` по образцу соседних, строка справки в
шапке файла, упоминание в runbook деплоя админ-бота.

### Задача 8. Тесты

Оба проекта, целевыми прогонами по затронутым файлам; полный прогон один раз
перед коммитом. Тест на живой Postgres обязателен там, где есть SQL между
схемами (урок 17.09: дефект `ON CONFLICT` тесты без живой базы не ловили).

## Порядок выката

1. Рабочий бот: миграция `0012` **ролью bot**, затем код, затем рестарт.
2. Админ-бот: `rsync`, затем `sudo raketa-admin-bot-update` (миграции
   применит сам), выключатель включить отдельной командой после проверки.

## Чего не делаем

- Не переводим удаление заказов химчистки на мягкое: в `bot.py` пятнадцать
  тысяч строк, и каждый запрос к заказам пришлось бы учить слову «удалён».
- Не различаем переоформление и пропажу (решение 8).
- Сделку в CRM не удаляем — API не умеет (факт 11).

## Примечание владельцу (не код)

Правильный порядок действий для мастера: **сначала удалить неверный заказ,
потом заводить новый**. Тогда робот освободит сделку и переоформленный заказ
подхватит её же — дубля в CRM не будет вовсе. В обратном порядке дубль
неизбежен: в момент проведения нового заказа старый ещё жив и его сделка
занята законно.
