# Google Calendar (этап 2) — план реализации

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Робот узнаёт о заказе в день, когда владелец записал его в календарь, а не через неделю после закрытия в боте: готовит сделку заранее, видит отмены (сейчас не видит никогда) и заполняет «Комментарий к заказу» и «Район города», которые в уборке всегда пустые.

**Architecture:** Новая функция `gcal` в том же сервисе, рядом с `amo_sync` и `carpets`. Цепочка: инкрементальный обмен с Google Calendar (только изменения, включая удаления) → разбор записи (район, услуга, комментарий, телефон) → сопоставление со сделкой в амо → заполнение и передача в работу. Переиспользуем ядро: клиент amoCRM с режимом репетиции, канон телефона, хранилище `adminbot`, карточки-вопросы, вечернюю сводку. Своя таблица (ключ — id записи календаря), поэтому повторный проход ничего не портит.

**Tech Stack:** Python 3.10+ (на сервере 3.10.12), `google-auth` (подпись служебного ключа и получение токена), `aiohttp` для запросов к API, остальное — как в v1.

## Что уже проверено (2026-08-26)

- **Google API с боевого сервера доступен**: `https://www.googleapis.com/calendar/v3/...` отвечает 401 (нужен только ключ), имя резолвится. Это не Telegram, обходных путей не потребуется.
- **Механика изменений подтверждена документацией Google** (`developers.google.com/workspace/calendar/api/guides/sync`):
  - первый обмен — полный, с фильтром `timeMin`; в конце ответа приходит `nextSyncToken` («закладка»);
  - дальше — только `syncToken`: приходят лишь изменившиеся записи. **Удалённые записи возвращаются только здесь**, со `status: cancelled`. Обычная выдача их не показывает — поэтому отмены иначе не поймать;
  - с `syncToken` нельзя менять фильтры (`timeMin`, `orderBy` и пр.) — иначе 400. Разрешён `singleEvents`, `maxResults`, `pageToken`;
  - протухшая закладка → 410 `fullSyncRequired`: чистим курсор и делаем полный обмен заново.
- **Состав календаря** (462 записи за полгода, `tgbot-v1/recon/02-calendar.md` + пересчёт 2026-08-26):
  заказы 339 (73%), блокировки мастеров «⛔️Никита»/«⛔️Дима» 112, теплоходы 6, «Перемыв» 7, «⁉️Перенос…» 1.
  Услуги в заголовках: диван 166, матрас 47, мебель 39, уборка 17, стулья 14, ковролин 13, кресло 6, окна 2, единичные (кровать, подушка, коляска, санузел, кухня, лежанка, изголовье, каркас, уголок).
  Телефон извлекается посимвольным сканером из 334 из 339 заказов (98,5%); простая регулярка справляется хуже — берём канон бота `adminbot/phone.py`.
- **Права**: календарь `raketaclean52@gmail.com`, тайм-зона Europe/Moscow, встречается Europe/Simferopol — читаем тайм-зону записи, а не предполагаем.

## Решения владельца (2026-08-26)

1. **По новой записи робот готовит сделку целиком**, не дожидаясь закрытия заказа в боте: находит лид в амо (или создаёт), заполняет услугу, дату, адрес, комментарий, район, передаёт в работу и дожидается автосделки сейлзбота.
2. **Отмена (запись удалена) → карточка-вопрос владельцу** с кнопками. Робот сам сделку не закрывает: удаление бывает и переносом, и случайностью, а закрытая сделка портит статистику.
3. **«Комментарий к заказу» = весь текст записи, кроме телефонов и кодов доступа** (домофон, кейбокс, пароль wi-fi).
4. **Доступ — служебный аккаунт Google** с правом чтения. Ключ не протухает, участия владельца после настройки не требует.
5. **Перенос даты робот в амо не правит.** Фактическую дату впишет заказ из бота, когда мастер его закроет (движок это уже делает: `FIELD_ORDER_DATETIME` перезаписывается всегда).
6. **«Перемыв» — гарантийный выезд, сделку не заводить**, запись пропускать молча.
7. **Блокировки «⛔️…» пропускать.** Теплоходы (без телефона и цены) — **карточка владельцу с кнопкой «Завести сделку»**, сам робот их не заводит.
8. **Старт — только новые записи после включения.** Уже лежащие в календаре будущие заказы робот в работу не берёт (они дойдут обычным путём, из бота).
9. **«⁉️» или «Перенос» в заголовке = дата не твёрдая**: робот ждёт, пока владелец уберёт пометку, и только потом заводит сделку.
10. **Заказ без телефона — пропустить молча** (5 случаев из 339). Он придёт из бота после выполнения.
11. **Услуга — точная, где однозначно** (таблица выше); диваны/кресла/стулья не детализируем.
12. **Непонятная приставка района — поле пустое**, догадки запрещены.

13. **Сделка по календарю останавливается на «Заказ оформлен»** (`REAL_STAGE_CREATED`). Дальше не двигаем: мастера в записи календаря нет, а этап «Мастер назначен» при пустом поле «Специалист» — неправда в CRM. Автозадачу «Назначь мастера» робот не закрывает — это работа владельца. Оперативность сохраняется полностью: сделка заведена и заполнена в день записи.

## Уточнения первого боевого дня (2026-08-27)

    показывал владельцу пустоту. В боевом режиме тихо: там это был бы спам.

**Step 2: Implement**

`parse_event(raw) -> ParsedEvent` — один разбор на все случаи:

- `status == "cancelled"` → `EventKind.CANCELLED`, остальные поля не нужны (в удалённой записи Google отдаёт только id);
- заголовок начинается с «⛔️» → `BLOCK`;
- в заголовке «⁉️» или «перенос» → `UNSETTLED`;
- услуга «перемыв» → `REWASH`;
- нет телефона и заголовок совпал со списком теплоходов → `BOAT`;
- нет телефона и не теплоход → `SKIP` (решение 10);
- иначе `ORDER`.

Разбор заголовка: `«<Приставка>! <Услуга>, <Имя>»`, устойчив в 94% случаев; отклонения — запятая вместо «!» и полное отсутствие приставки, оба варианта поддерживаем.

Телефоны — посимвольным сканером из `adminbot/phone.py` по описанию **и** заголовку; порядок сохраняем, первый считаем основным.

Комментарий: из описания убираем строки, содержащие телефон, и строки со словами `код`, `пароль`, `домофон`, `кейбокс`, `wi-fi`, `сеть`, `keybox`; пустые строки схлопываем. Всё остальное — включая цены и жаргон («Сушка 40», «Нз 1800₽») — сохраняем: решение 3.

Дата заказа — из `start.dateTime` с тайм-зоной **самой записи**; для all-day записей — `start.date`.

## Фаза 2 — проведение сделки по записи

### Task 5: Сопоставление записи со сделкой

**Files:**
- Create: `adminbot/gcal/matcher.py`
- Test: `tests/test_gcal_matcher.py`

Переиспользуем `adminbot/sync/matcher.py`: правила те же (приоритет воронки реализации, дата ±2 дня, чужие сделки не занимаем), но у записи календаря **нет суммы** — сопоставление идёт по телефону и дате. Ковровые и архивные воронки игнорируем (`PIPELINES_IGNORED`).

Отличие от заказа из бота: запись календаря смотрит **вперёд**, поэтому «сделка закрыта раньше даты записи» — не кандидат вовсе, а не повод для вопроса.

Тесты: одна открытая сделка в реализации → берём; лид в первичной → берём; закрытая сделка на ту же дату → не трогаем (владелец провёл руками); две открытые сделки → вопрос владельцу; сделка уже привязана к другой записи календаря → не занимаем.

**Commit** — `feat: сопоставление записи календаря со сделкой`

### Task 6: Движок: заполнение и передача в работу

**Files:**
- Create: `adminbot/gcal/engine.py`
- Test: `tests/test_gcal_engine.py`

Пути повторяют v1, чек-лист пишется после каждого шага:

- **А. Есть сделка в воронке реализации** → дозаполнить пустые поля (услуга, дата, адрес, комментарий, район), этап не двигать.
- **Б. Есть лид в первичной** → заполнить те же поля → «Передано в работу» → дождаться автосделки сейлзбота (до 40 минут, как в v1) → дозаполнить и остановиться.
- **В. Ничего нет** → найти/создать контакт по телефону → создать лид в первичной → путь Б.
- **Финальный этап сделки не трогаем никогда** (уже проведена руками — только привязываем).

Что робот пишет и чего не пишет:

| Поле | Календарь |
|---|---|
| Услуга | ставит, если пусто (точную, таблица выше) |
| Дата и время заказа | ставит при заведении; **при переносе не правит** (решение 5) |
| Адрес | ставит, если пусто |
| Комментарий к заказу | ставит, если пусто |
| Район города | ставит, если пусто и приставка понятна |
| Специалист | **не трогает** — мастера в записи нет |
| Бюджет | **не трогает** — сумма чека известна только боту |
| Автозадачи | **не закрывает** — заказ ещё не выполнен |

Заполненное поле не перезаписываем — то же правило, что в v1: правки владельца в CRM важнее догадок робота.

**Commit** — `feat: движок календаря — заполнение и передача в работу`
