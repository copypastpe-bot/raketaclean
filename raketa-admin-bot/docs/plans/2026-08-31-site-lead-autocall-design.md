# Дизайн: автозвонок по заявке с сайта (autocall)

Дата: 2026-08-31. Статус: **одобрен владельцем 2026-08-31** (все решения согласованы в диалоге).
Основание: диалог с владельцем 2026-08-31; телефония onlinePBX уже интегрирована с амо.

> **Поправка по итогам стенда 2026-09-02.** Решение №2 ниже описывает схему звонка,
> которая на этой АТС не работает, — исправлено в коде и в `docs/deploy.md`
> (раздел «Что выяснил стенд 2026-09-02»). Кратко:
>
> - **Цепочку переадресации ведёт робот, а не АТС.** Правила «не ответил за 10
>   секунд — звони на мобильный» применяются только ко входящим звонкам, идущим по
>   схеме АТС; звонок роботом отдаётся командой через API и этих правил не видит
>   (4 прогона — цепочка не поднялась ни разу). Порядок «рабочий → личный» остался
>   тем же, каким его задумал владелец, только номера теперь в `PBX_MANAGER_DIAL`,
>   и на личный робот звонит сам — повтором через 5 минут.
> - **Голосовой отбивки не будет** (`call/now.json` не проигрывает аудио, модуль
>   «Приветствие» ломает переадресацию — ответ поддержки onlinePBX). Менеджер
>   отличает робота иначе: телефон зазвонил, а приложение АТС молчало.
> - Определитель у обоих плеч остался прежним: номер компании +7 904 043-75-23.

## 1. Цель

Клиент, оставивший заявку на raketaclean.ru, должен получить звонок в первые минуты,
а не через часы. Сегодня заявка ждёт, пока её заметят; реальный случай — владелец
перезвонил через 2 часа, клиент уже заказал у конкурента. Схема: робот замечает
новую сделку с сайта и командует АТС соединить менеджера с клиентом — телефон
менеджера звонит сам, даже если заявку никто не открыл.

## 2. Решения владельца (зафиксированы 2026-08-31)

1. **Звоним только по заявкам с сайта.** Признаки в амо: этап «Новый лид»,
   тег «Заявка с сайта», источник сделки «Сайт». Остальные заявки — сообщения
   и обычные входящие, по ним не звоним.
2. **Схема звонка**: АТС звонит менеджеру по уже настроенной в onlinePBX
   цепочке переадресации (рабочий мобильный → личный; номера хранятся в
   настройках АТС и `.env`, в git не попадают) → менеджеру проигрывается
   голосовая отбивка владельца («звонок клиенту по заявке, подробности в
   ТГботе») → АТС набирает клиента и соединяет. Оба плеча выходят с исходящего
   номера компании +79040437523: менеджер видит привычный определитель,
   клиент — номер компании, и его обратный перезвон попадает в АТС.
   Отбивка — единственное, что отличает автозвонок от обычной входящей
   заявки для менеджера (плюс сообщение в ТГ).
3. **Менеджер не взял** → повтор через 5 минут; после второй неудачи —
   сообщение админу в рабочий бот (состав сообщения обсуждается отдельно).
4. **Менеджер взял, клиент не ответил** → сообщение в бот «Попытка звонка
   не удалась, повтор через 10 минут» → повтор через 10 минут; после второй
   неудачи — сделка переносится на этап «Не было первого контакта», дальше
   владелец обрабатывает руками.
5. **Окно звонков: 10:00–20:00 МСК.** Заявка вне окна — звонок в ближайшие 10:00.
6. **Одновременно со звонком** менеджер получает сообщение в рабочем боте:
   ссылка на сделку + описание заявки (имя, услуга, текст). Уведомления о
   заявках в рабочем боте уже есть — для заявок с сайта делается своё сообщение.
7. Источник данных о заявке — письмо с сайта в ленте сделки (имя, телефон,
   услуга, страница-источник).

## 3. Архитектура (кто что делает)

- **admin-bot (этот репозиторий), новая фича `autocall`**: наблюдатель
  (опрос амо раз в ~30–60 сек: новые сделки с тегом «Заявка с сайта», созданные
  после включения фичи), окно звонков и очередь «ночных», команды onlinePBX,
  определение исхода попытки, повторы по правилам владельца, перенос этапа
  «Не было первого контакта» (через нашу write-интеграцию амо), сообщения
  о неудачных попытках.
- **tgbot-v1**: специальное сообщение менеджеру на событие «заявка с сайта»
  (вебхук амо уже приходит туда, формат уведомления уже есть — расширить).
  Отдельная задача в том репозитории, в его сессии.
- **onlinePBX**: сценарий «позвонить менеджеру → отбивка → набрать клиента»,
  загруженная отбивка владельца. Настраивается в личном кабинете АТС.

Границы — как у всех фич админ-бота: своё состояние в схеме `adminbot`
(сделка → цепочка попыток звонков), в таблицы рабочего бота не пишем,
свой выключатель (по умолчанию выключено), режим репетиции.

## 4. Жизненный цикл заявки

1. Письмо с сайта → амо создаёт сделку (этап «Новый лид», тег, источник «Сайт»).
2. Наблюдатель админ-бота видит новую сделку с тегом → заводит цепочку попыток.
3. Если сейчас окно 10:00–20:00 МСК — звонок сразу; иначе — очередь на 10:00.
4. Попытка: АТС звонит менеджеру → отбивка → набор клиента.
   - Соединились → цепочка закрыта, готово.
   - Менеджер не взял → правило 3 (повтор 5 мин → сообщение админу).
   - Клиент не взял → правило 4 (сообщение + повтор 10 мин → этап
     «Не было первого контакта»).
5. Предохранитель: не больше 4 попыток на одну сделку суммарно, что бы ни
   происходило; после лимита — сообщение админу и остановка по этой сделке.

## 5. Надёжность

- **Идемпотентность**: намерение позвонить записывается в БД до команды АТС;
  после падения и перезапуска робот не позвонит по той же сделке второй раз.
- Сделки, созданные до включения фичи, — владельца; робот их не трогает.
- Амо или АТС недоступны → ретраи с паузами, после 30 минут молчания — алерт
  владельцу (как в amo_sync).
- **Репетиция**: робот решает и пишет владельцу «позвонил бы сейчас по сделке
  №…», но не звонит и не пишет менеджеру; состояние репетиции — только в
  памяти, не в БД (боевой запуск должен начать с чистого листа).
- Телефоны в логах маскируются; в сообщениях менеджеру и владельцу — полные
  (правило владельца 2026-08-26).
- Kill switch: `--autocall-on/--autocall-live` по образцу остальных фич.

## 6. Проверка и запуск

1. **Экзамен на истории**: выбрать сделки с тегом «Заявка с сайта» за последние
   30–60 дней, прогнать фильтр и разбор письма из ленты — 0 чужих сделок,
   принятых за сайтовые; имя/телефон/услуга извлекаются.
2. Автотесты по TDD: окно времени, ветки повторов, лимит попыток, идемпотентность.
3. **Стенд с АТС**: тестовые звонки, где «клиент» — номер владельца; проверяем
   отбивку, соединение и определение исходов до подключения живых заявок.
4. Репетиция 1–2 дня на живых заявках (решает, пишет владельцу, не звонит).
5. Боевой старт + неделя наблюдения (каждая цепочка — отчёт владельцу).

## 7. Нужно от владельца

- Ключ API onlinePBX из личного кабинета (покажем, где взять).
- Этап «Не было первого контакта» в воронке (создать, если ещё нет).
- Голосовая отбивка — после настройки сценария в АТС.
- Состав сообщений менеджеру (обсудить перед стройкой Telegram-части).

## 8. Открытые технические вопросы к этапу планирования (не требуют владельца)

- Точный метод запуска звонка в api2.onlinepbx.ru и формат авторизации
  (документация доступна из личного кабинета; при нужде — поддержка АТС).
- Как в команде АТС адресовать существующую цепочку переадресации менеджера
  (внутренний номер / сотрудник), а не набирать мобильный напрямую — чтобы
  «не взял на рабочем → личный» отработал внутри одной попытки.
- Как определять исход попытки (менеджер взял / клиент взял): события АТС
  (вебхук) или опрос истории звонков — что доступно в тарифе.
- Можно ли повесить отбивку именно на сценарий обратного звонка в кабинете АТС.
- Задержка «письмо → сделка в амо» — померить на живой заявке; если велика,
  запасной вариант — триггер от письма по IMAP (механика чтения почты уже
  есть в фиче carpets).
- Транспорт сообщений менеджеру от админ-бота: рекомендация — отправка через
  токен рабочего бота в режиме «только отправить» (конфликтов с его поллингом
  нет, менеджер видит сообщения от привычного бота); альтернатива — внутренний
  endpoint в tgbot-v1. Решить на планировании вместе с задачей в tgbot-v1.
- Как из ленты сделки вытащить текст письма (amo API: примечания типа email
  у сделки/контакта).
