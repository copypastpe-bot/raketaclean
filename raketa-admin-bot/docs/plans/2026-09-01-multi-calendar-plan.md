# План: робот читает несколько календарей

Дата: 2026-09-01. Основание: решение владельца 2026-09-01 — календарь бригадира
по клинингу («Клининг Оля», внутри аккаунта `raketaclean52@gmail.com`) должен
обрабатываться так же, как основной.

## 1. Зачем

Уборки уехали в отдельный календарь: мебель и ковры остались у мастеров в основном,
клининг ведёт бригадир в своём. Робот читает ровно один календарь, поэтому заказы
на уборку в CRM больше не попадают — их нужно оформлять руками.

## 2. Что уже проверено на живых данных (2026-09-01)

- Доступ роботу выдан, календарь читается (HTTP 200, «Клининг Оля», Europe/Moscow).
- Разбор записей работает **без единой правки**: обе записи разобраны верно —
  услуги (включая комбинацию «Уборка + Мебель»), районы («Ниже!» → Нижегородский,
  «Сор!» → Сормовский), телефон, имя, адрес, дата.
- Пересечений между календарями нет: в основном за 25.08–20.09 — 42 записи,
  вся мебель, ковры и выходные мастеров; уборки только во втором.
- Перенос записи между календарями безопасен: `ea7ikdff…` («Сор!Уборка, Лариса»)
  обработана 30.08 из основного календаря и 01.09 перенесена в календарь бригадира;
  идентификатор Google при переносе сохраняется, а он и есть ключ в `gcal_events`.

## 3. Где именно зашит «один календарь»

1. `adminbot/config.py` — `GCAL_CALENDAR_ID`, одна строка.
2. `migrations/005_gcal.sql` — `gcal_cursor` объявлена как таблица ровно из одной
   строки (`id smallint PRIMARY KEY DEFAULT 1 CHECK (id = 1)`). Второй календарь
   затирал бы закладку первого, и каждый обмен начинался бы заново.
3. `adminbot/gcal/watcher.py` — один `calendar`, один вызов `fetch` за проход.

Клиент `GoogleCalendar` менять не нужно: он уже принимает `calendar_id`.

## 4. Решения по устройству

- **Один наблюдатель на все календари**, а не по наблюдателю на календарь.
  Причина: незавершённые записи (`store.pending()`) не разделены по календарям,
  и два наблюдателя обрабатывали бы одну и ту же запись одновременно — лишние
  обращения в amoCRM и двойные сообщения владельцу. Проход: по очереди забрать
  изменения из каждого календаря, затем один общий проход по незавершённым.
- **Закладка — на каждый календарь.** Миграция 008 переводит `gcal_cursor` на
  ключ `calendar_id`.
- **Старую закладку не теряем.** Потеря закладки основного календаря = следующий
  обмен приходит как полная перезагрузка. Миграция сохраняет существующую строку
  с пустым ключом, а код при первом чтении отдаёт её первому календарю из настроек
  и тут же перезаписывает уже с его адресом («усыновление» legacy-строки).
- **Сбой одного календаря не мешает другому**: обмен по каждому обёрнут отдельно,
  закладка сохраняется только по тому календарю, чья пачка разобрана.
- **Первый обмен по новому календарю только запоминает** — правило не меняется
  (решение владельца 8). Записи, лежащие в календаре бригадира на момент
  включения, робот пометит «до включения» и трогать не станет. Нужную запись
  владелец проводит вручную: `--gcal-run=<id записи>`.

## 5. Задачи

### Задача 1: Настройка — список календарей
`config.py`: `gcal_calendar_ids: tuple[str, ...]` вместо одной строки, значение
`GCAL_CALENDAR_ID` разбирается по запятой, пробелы и пустые элементы отбрасываются.
Одно значение работает как раньше. Тесты: одно значение, два значения, мусор
в разделителях, пустая настройка → фича не поднимается. Commit.

### Задача 2: Миграция 008 и слой базы
`migrations/008_gcal_multi_calendar.sql`: снять ограничение «одна строка», добавить
`calendar_id text NOT NULL DEFAULT ''`, сделать его первичным ключом. Существующая
строка остаётся с пустым ключом.
`db.py`: `get_calendar_cursor(pool, calendar_id)` — своя строка, иначе legacy-строка
(и только для первого календаря); `save_calendar_cursor(pool, calendar_id, …)` —
пишет по ключу и удаляет legacy-строку, когда она усыновлена.
Тесты на живом Postgres (как остальные тесты схемы): две закладки не мешают друг
другу; legacy-строка достаётся первому календарю ровно один раз. Commit.

### Задача 3: Хранилище
`store.py`: в протоколе, `MemoryCalendarStore` и `PgCalendarStore` — `cursor(calendar_id)`
и `save_cursor(calendar_id, sync_token, sync_from)`. В памяти — словарь по календарю.
Тесты: закладки не пересекаются. Commit.

### Задача 4: Наблюдатель
`watcher.py`: `calendars` — список; проход по каждому со своей закладкой и своим
`first_run`; общий проход по незавершённым — один раз в конце; в отчёт добавить
разбивку по календарям; сбой одного календаря не отменяет обмен по другим.
Тесты: две пачки из двух календарей обработаны за один проход; закладка каждого
сохранена своя; сбой первого календаря не мешает второму; незавершённые
обрабатываются один раз, а не по разу на календарь. Commit.

### Задача 5: Сборка и команды владельца
`main.py`: список `GoogleCalendar`, в логе старта — все календари.
`tg/bot.py`: `/status` и `/calendar` — по каждому календарю.
`deploy/update.sh`: `--gcal-check` и `--gcal-reset` — по всем календарям.
`scripts/check_calendar.py`: то же.
`.env.example`: пример с двумя календарями через запятую. Commit.

### Задача 6: Деплой и включение
1. `rsync` кода на сервер, затем `sudo raketa-admin-bot-update` (двухшаговый деплой,
   §9 раннбука; проверить, что миграция 008 видна в выводе шага 4).
2. `--gcal-check` — робот показывает ближайшие записи обоих календарей, в CRM
   ничего не пишет.
3. Первый боевой проход: календарь бригадира запоминает свои записи, не трогая их.
4. Запись «Ниже! Уборка + Мебель Влад» (03.09) — по решению владельца: провести
   вручную `--gcal-run=7rhj23gno86bc6baee8egqtpm7` или оставить ему.
5. Наблюдение: следующая новая запись у бригадира должна дойти до CRM сама.

## 6. Чего этот план НЕ делает

- Не меняет разбор записей: формат у бригадира тот же (проверено).
- Не трогает ковры, заказы и автозвонок.
- Не заводит отдельные правила для «уборочных» сделок: услуга «Уборка» уже
  поддержана и раньше приходила из основного календаря.
