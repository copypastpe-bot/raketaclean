# ТЗ для tgbot-v1: адрес заказа берётся из календаря, а не из карточки клиента

Дата: 2026-09-06. Автор задачи: владелец. Подготовлено в сессии проекта
`raketa-admin-bot`, исполняется **в репозитории `tgbot-v1`** (сессию открывать
из его папки — там свои правила и своя память).

## Зачем это нужно (в двух словах)

Отчёт о выполненном заказе, который бот кидает в чат подтверждений, показывает
адрес из карточки клиента. Тот заполнялся когда-то импортом из CRM и с тех пор
живёт своей жизнью. Реальный адрес работы владелец вносит в календарь — по нему
едет мастер, и он же попадает в актуальную сделку amoCRM. Владелец хочет, чтобы
адрес был свойством **заказа**, а не человека.

Пример от 2026-09-06 (клиентка Ирина, сделка 31587353):

| Где | Что написано |
|---|---|
| карточка клиента в базе бота | `Менделеева 15 а кв 99. Домофон 99` |
| запись календаря и сделка амо | `Менделеева д 15а, кв 99, п 3, эт 4, со стороны двора` |
| отчёт о выполнении в чат | адрес из карточки — то есть устаревший |

Некритично (мастер едет по календарю), но вызывает вопросы и портит историю.

## Что уже выяснено — не перепроверять

1. **У заказа нет своего адреса.** В боевой схеме `public.orders` колонки адреса
   нет вовсе: есть суммы, оплата, мастер, бонусы, оценка, перемыв — адреса нет.
   Проверено по `recon/data/bot_db_schema.sql`, таблица начинается на строке 1222.
2. **Адрес живёт у клиента:** `clients.address`, запасной вариант
   `clients.last_order_addr`. Заполнялись импортом из выгрузки amoCRM
   (`bot.py:5572` — `sanitized.get("Адрес")`, запись в клиента — `bot.py:5747`).
3. **Отчёт печатает карточку клиента:** `bot.py:13999` — `client_address_val =
   client.get("address")`, вывод строки — `bot.py:14223` (`📍 Адрес: …`),
   отправка в `ORDERS_CONFIRM_CHAT_ID`.
4. **Актуальный адрес уже есть в amoCRM.** Админ-бот переносит его из записи
   календаря в поле сделки «Адрес» (`field_id = 18639`), воронка реализации
   `4482787`. Обновляет при каждой правке записи — это источник правды.
5. **Админ-бот сам в базу бота записать не может**: его жёсткое правило —
   никогда не писать в таблицы рабочего бота, только читать. Поэтому заполнять
   адрес заказа должен сам `tgbot-v1`.
6. **Утечка на стороне админ-бота уже закрыта** (коммит `13e0ede`, в бою с
   2026-09-06 13:18): проведение заказа больше не затирает адрес в сделке
   амо адресом из карточки клиента. Раньше затирало.

## Что сделать

### 1. Завести у заказа собственный адрес

Миграция в базе рабочего бота: колонка `address text` в `public.orders`.
Заполняется на момент проведения заказа мастером и дальше не меняется —
это адрес, куда фактически ездили.

### 2. Заполнять её из актуальной сделки amoCRM

При проведении заказа: найти по телефону клиента открытую сделку в воронке
реализации (`4482787`), взять поле «Адрес» (`18639`) и записать в заказ.
Ходить в amoCRM бот уже умеет — `notifications/amocrm_api.py`.

Порядок источников, сверху вниз:

1. адрес открытой сделки реализации в амо (он приходит из календаря);
2. `clients.address` / `clients.last_order_addr` — если сделки нет или в ней пусто;
3. пусто — если нет ничего (в отчёте показывать «—», как сейчас).

**Проведение заказа не должно зависеть от амо.** Недоступная CRM, таймаут,
не найденная сделка — не повод не дать мастеру закрыть заказ: в этом случае
работает пункт 2, и заказ проводится как раньше.

### 3. Отчёт в чат печатает адрес заказа

`bot.py:14223` — вместо `client_address_val` подставить адрес заказа.
Остальные места, где показывается адрес клиента (карточка клиента, поиск),
не трогать: там речь именно о клиенте.

### 4. По желанию владельца: обновлять карточку клиента

Владелец сказал: «в карточке клиента как будто вообще нет смысла его хранить,
но можно и перезаписывать адрес последнего заказа». Предлагаемое решение:
`clients.last_order_addr` обновлять адресом проведённого заказа, а
`clients.address` не трогать — пусть остаётся подсказкой при заведении заказа
без календаря. Решение подтвердить у владельца перед реализацией.

## Ограничения и осторожности

- `bot.py` — около 13 тысяч строк. Логику поиска адреса вынести в отдельный
  модуль (образец — `notifications/client_messaging.py`), в самом `bot.py`
  оставить вызов. Правило проекта: интеграции без разрастания `bot.py`.
- Персональные данные (адреса, телефоны) в git не попадают; в логах телефон
  маскируется до последних четырёх цифр.
- Заказы за прошлые даты задним числом не переписывать: колонка заполняется
  только для новых проведений. История остаётся как есть.

## Как проверить, что получилось

1. Взять клиента, у которого адрес в календаре отличается от карточки
   (можно сделать нарочно: уточнить адрес в записи календаря).
2. Провести заказ мастером.
3. Ожидается: в чат подтверждений приходит адрес **из календаря**; в
   `orders.address` лежит он же; сделка в амо не изменилась.
4. Отдельно проверить заказ клиента без сделки в амо: заказ проводится,
   адрес берётся из карточки, поведение как раньше.

## Что останется сделать после этого в raketa-admin-bot

Когда у заказа появится свой адрес, админ-бот должен читать его, а не карточку
клиента. Правка одна: `adminbot/db.py:43`, сейчас там

```sql
COALESCE(NULLIF(TRIM(c.address), ''), NULLIF(TRIM(c.last_order_addr), '')) AS address
```

нужно добавить первым источником `o.address`. Делается в сессии проекта
`raketa-admin-bot` после того, как колонка появится в базе.
