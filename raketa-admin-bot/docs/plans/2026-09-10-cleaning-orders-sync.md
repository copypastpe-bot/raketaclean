# ТЗ: проводить в амо заказы клининг-контура

Дата: 2026-09-10. Автор задачи: владелец. Проект: `raketa-admin-bot`, функция
amo_sync. Размер: фича (новый источник заказов, миграция, выключатель).

## Зачем (в двух словах)

Робот проводит в CRM заказы химчистки из таблицы `public.orders` рабочего бота.
Клининг-контур того же бота (с 2026-05-21) пишет заказы в **свою** таблицу
`public.cleaning_orders`, и робот её не читает: уборки в амо не проводятся
вовсе. Дизайн 2026-08-24 считал, что уборка приходит через `orders` с мастером
Олей, — это не так. Нужно, чтобы уборки шли по тому же пути, что и химчистка:
найти сделку клиента, заполнить, довести до «Успешно реализовано», закрыть
автозадачи, отчитаться владельцу.

## Решения владельца (2026-09-10)

1. «Специалист» в сделке уборки — всегда **Ольга Скоропашкина** (`enum_id 952251`),
   кто бы ни был бригадиром. Бригадир — в примечание.
2. Оплата: «Наличные» → «Наличка» (235849); «Расчётный» → «Безнал» (235857);
   «Подарочный сертификат» → «Сертификат + деньги» (884545). «Карта» →
   «Перевод на карту» (235851) — допущение агента по аналогии с «Карта Дима»
   / «Карта Женя»; владелец не возражал.
3. Хвост: **с момента включения**, старые уборки владелец закроет сам.
4. «Услуга» — всегда «Уборка» (772345). Окна и прочее живут в комментарии,
   который уже переносится из календаря.
5. Оценки клиента у клининга нет → задачу «Получить ОС» не закрываем
   (решение 9 без изменений). Владелец вопрос не комментировал — оставить так,
   отметить в отчёте о выполнении.

## Что уже выяснено — не перепроверять

1. `public.cleaning_orders` (`tgbot-v1/cleaning/schema.py:24`): `id`, `client_id`
   → `clients`, `foreman_id` → `cleaning_foremen (fn, ln, phone)`, `address`
   (свой! у химчистки адреса в заказе нет), `total_amount`, `bonuses_used`,
   `bonuses_earned`, `happened_at` (= момент проведения, как `orders.created_at`),
   `deleted_at` (не NULL — заказ удалён, пропускать). Оплаты — отдельной
   таблицей `cleaning_order_payments (order_id, method, amount)`, методов может
   быть несколько; «основной» = первый вставленный (так считает и сам бот,
   `cleaning/handlers.py`). Телефон и имя клиента — из `clients` (`phone`,
   `full_name`); нормализация — `adminbot.phone.last10`, как в `_order_from_row`.
2. Права на чтение у роли `adminbot` есть: `GRANT SELECT ON ALL TABLES IN SCHEMA
   public` (`docs/deploy.md:117`), таблицы клининга старше установки. Всё равно
   проверить одним `SELECT count(*)` на сервере перед включением.
3. Движок `adminbot/sync/engine.py` работает с `adminbot.models.Order` и ничего
   не знает о таблицах: источник — `PgOrderSource` (`sync/watcher.py:165`,
   протокол `OrderSource.pending()`), хранилище — `PgLinkStore` поверх
   `adminbot.amo_links` (PK `order_id`). **Номера `cleaning_orders.id` и
   `orders.id` пересекаются** — в одну таблицу связок их класть нельзя.
4. «Услугу» движок выводит из имени мастера (`service_by_master`,
   `_service_enum`), «Специалиста» — из имени/телефона мастера через
   `SpecialistIndex` (`sync/specialists.py`). Для уборки оба значения заданы
   решением владельца, а не мастером.
5. Оплата: `PAYMENT_ENUM_BY_METHOD` (`sync/engine.py:461`), «р/с» = безнал →
   тип клиента «Юр лицо», и при `awaiting_wire_payment` сделка останавливается
   на «Заказ выполнен». У клининга признака «ждём оплату» нет: оплата вносится
   при проведении → считать полученной.
6. Отчёт владельцу и карточки: «Заказ №N» собирается в `tg/cards.py:_order_line`
   и `sync/backlog.py:94`; сводка дня — `Reconciler` + `PgSummarySource`
   (`sync/reconcile.py`), тоже поверх `amo_links`.
7. Занятые сделки: матчер исключает сделки, уже привязанные к другим заказам
   того же телефона (`db.fetch_taken_lead_ids` по `amo_links`). Уборка и
   химчистка одному клиенту в один день — две сделки (памятка владельца
   2026-09-02), поэтому «занятость» должна смотреть на ОБЕ таблицы связок.
8. Выключатели: у каждой функции свой (`AMO_SYNC_ENABLED`/`_DRY_RUN`,
   `CARPETS_*`, `GCAL_*`, `AUTOCALL_*`), читаются в `config.py`, печатаются в
   `/status` и в шаге «5. Выключатели» скрипта обновления. Репетиция держит
   состояние в памяти (`MemoryLinkStore`), чтобы не красть работу у боя.

## Что сделать

### 1. Модель: `Order` получает переопределения

`adminbot/models.py`, `Order`: добавить

```python
kind: str = "order"                       # "order" | "cleaning" — для текстов и журналов
service_kind: Optional[str] = None        # None → вывести из мастеров, как сейчас
specialist_enums: Optional[tuple[int, ...]] = None   # None → SpecialistIndex по мастерам
```

`Engine._service_enum` / `_master_enums` сначала смотрят переопределения.
`kind` используется только для подписи: «Заказ №N» / «Уборка №N»
(`tg/cards.py`, `sync/backlog.py`, логи движка) — вынести подпись в одно место,
например `Order.label` → «Заказ» | «Уборка».

### 2. Источник: `db.py` — чтение уборок

`_SELECT_CLEANING_ORDERS` + `_cleaning_order_from_row`:

- `order_id = co.id`, `kind="cleaning"`, `created_at = co.happened_at`,
  `amount_total = co.total_amount`, `address = co.address`,
  `client_name = c.full_name`, `phone10 = last10(c.phone)`;
- `masters = [(fn + ' ' + ln, phone)]` бригадира — только для примечания
  «Мастер: …»; `specialist_enums = (952251,)`; `service_kind = "cleaning"`;
- `payment_method` = метод первой строки `cleaning_order_payments` по `id`
  (ключи для маппинга: «наличные», «карта», «расчётный», «подарочный
  сертификат» — добавить в `PAYMENT_ENUM_BY_METHOD`; «расчётный» считать
  безналом в `_is_wire` — переименовать проверку в набор `WIRE_METHODS`);
- `awaiting_wire_payment = False`, `rating_score = None`;
- `is_repeat_client`: у клиента есть более ранний заказ **в любой из двух
  таблиц** (по `client_id` для `cleaning_orders`, по телефону для `orders`);
- `WHERE co.deleted_at IS NULL AND co.happened_at >= $1`.

`fetch_cleaning_orders_since` / `fetch_cleaning_orders_by_ids` /
`fetch_unprocessed_cleaning_orders` — зеркально существующим.

### 3. Хранилище: своя таблица связок

Миграция `010_cleaning_links.sql`: `adminbot.cleaning_links` и
`adminbot.cleaning_actions` — копия `amo_links`/`amo_actions` из `001`
(`order_id` = `cleaning_orders.id`). `PgLinkStore` параметризовать именами
таблиц (или сделать подкласс) — движок, карточки и сводка получают хранилище
и ничего не знают о таблице.

`fetch_taken_lead_ids` (и его аналог для уборок) — `UNION` по обеим таблицам
связок: сделку, занятую химчисткой, уборка не берёт, и наоборот.

### 4. Сборка в `main.py`

Второй набор: `PgCleaningSource` → `Watcher` → тот же класс `Engine` с тем же
`specialists`/`services`, но своим хранилищем и своими флагами:

- `CLEANING_SYNC_ENABLED` (по умолчанию 0), `CLEANING_SYNC_DRY_RUN` (по
  умолчанию 1), `CLEANING_BACKLOG_FROM` (по умолчанию — дата включения; без
  значения хвост не трогать);
- в репетиции — `MemoryLinkStore`, как у заказов;
- вопросы владельцу и отчёт «проведено» — те же отправители (`on_question`,
  `on_done`), подпись берётся из `Order.label`; кнопки карточки-вопроса должны
  различать вид заказа (`CHOICE_PREFIX` + kind), иначе ответ по «Уборке №5»
  уйдёт в «Заказ №5»;
- `/status` и шаг «5. Выключатели» — строка «уборки: ВКЛ/ВЫКЛ, режим»;
- вечерняя сверка: уборки в том же сообщении (второй `SummarySource` или
  объединение внутри `Reconciler`) — одна картина дня, не два сообщения.

Пауза (`amo_sync_paused`) — общая на оба потока: владелец нажимает одну кнопку.

### 5. Тесты

- карточки: подпись «Уборка №N», callback различает вид.
- репетиция уборок ничего не пишет ни в амо, ни в базу.

## Вне задачи

- Старые уборки (до включения) — владелец закрывает сам.
- Ковровый контур и календарь не меняются; календарь по-прежнему заводит
  сделку заранее, уборка её подхватывает как обычный заказ.
- Письма клиенту о выполнении уборки шлёт рабочий бот, здесь не трогаем.
