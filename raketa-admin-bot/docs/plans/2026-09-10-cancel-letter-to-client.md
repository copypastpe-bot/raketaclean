# ТЗ для tgbot-v1: письмо клиенту «заказ отменён» по закрытой сделке амо

Дата: 2026-09-10. Автор задачи: владелец. Подготовлено в сессии проекта
`raketa-admin-bot`, исполняется **в репозитории `tgbot-v1`** (сессию открывать
из его папки — там свои правила и своя память). Парное ТЗ админ-бота:
`raketa-admin-bot/docs/plans/2026-09-10-cancel-tasks-and-reason.md`.

## Зачем (в двух словах)

Заказ отменяется: владелец удаляет запись из календаря, админ-бот (по кнопке
владельца) закрывает сделку амо как «Закрыто и не реализовано» и ставит в ней
«Причина закрытия = Пропала потребность». Клиент об этом ничего не получает,
хотя рабочий бот ему уже писал «Ваш заказ принят» и, возможно, спрашивал
подтверждение. Владелец хочет, чтобы клиенту уходило письмо об отмене —
через очередь писем рабочего бота, с её каналами, лимитами и правилами.

Админ-бот в очередь писать не может (его жёсткое правило: таблицы рабочего
бота — только чтение). Поэтому сигнал идёт через карточку амо, как с галочкой
«веду сам» (`AMO_FIELD_OWNER_HANDLES`): рабочий бот сам замечает закрытую
сделку с нужной причиной и сам ставит письмо в очередь.

## Решения владельца (2026-09-10)

1. Письмо уходит по **любой** сделке, закрытой с причиной «Пропала
   потребность» — и закрытой роботом, и закрытой владельцем руками в амо.
   Причина в карточке и есть команда «сообщи клиенту».
2. Только тем клиентам, которым рабочий бот по этой сделке **уже писал или
   пытался писать** — то есть есть строка в `order_confirmations`
   (любой статус: planned / confirmed / refused / owner_notified / dropped).
   Клиенту без такой строки не пишем: бот с ним про этот заказ не говорил.
3. Текст письма (дословно, `{{date}}` — дата работы):

   ```
   Ваш заказ на {{date}} отменён. Если это ошибка или захотите записаться снова, просто свяжитесь удобным способом. Ваша raketaclean.ru
   ```

4. Выключатель — тот же, что у письма «Ваш заказ принят»:
   `CLIENT_MESSAGING_ENABLED` (+ `CLIENT_MESSAGING_DRY_RUN` для репетиции).
   Отдельного ключа не заводить.

## Что уже выяснено — не перепроверять

1. Проход разговора с клиентом: `bot.py:2230` `run_client_messaging_cycle`,
   раз в `CLIENT_MESSAGING_INTERVAL_SEC` (600 с). Внутри —
   `_amocrm_poll_confirmations_once(client, dry_run=...)`. Новый шаг встаёт
   в этот же проход (или отдельной функцией, вызываемой из него).
2. Связь «письмо ↔ заказ ↔ сделка»: таблица `order_confirmations`
   (`bot.py:1053`): `lead_id` (лид первичной), `deal_id` (сделка реализации,
   может быть NULL), `client_id`, `phone_digits`, `order_at`, `status`,
   `outbox_id` (письмо-вопрос), `asked_sent_at`.
3. Очередь писем: `notifications/outbox.py`, `enqueue_notification(conn,
   rules, event_key=..., client_id=..., payload=...)`. Шаблоны — в
   `docs/notification_rules.json` (`NOTIFICATION_RULES_PATH`, `bot.py:497`),
   файл лежит в репозитории, деплой = git pull. Образец события с датой —
   `order_created` (`variables: date, time, address`); payload строится
   `letter_payload(order_at=..., address=...)` — формат даты брать оттуда же.
4. Отмена ещё не ушедшего письма-вопроса: `cancel_outbox_entry(conn, entry,
   reason)`; `_confirmation_before_send` (`bot.py:~2249`) и без нас отменит
   вопрос по закрытой сделке, но делать это сразу при обнаружении отмены
   чище: клиент не должен получить «подтверждаете заказ?» после «заказ
   отменён».
5. Сделка в амо: `AmoCRMAPIClient.fetch_lead(id)` (`notifications/amocrm_api.py`).
   Закрытый статус — `status_id == 143` («Закрыто и не реализовано», общий
   для всех воронок). Поле «Причина закрытия» — `custom_fields_values`,
   `field_id = 19215`, тип select; «Пропала потребность» — `enum_id = 8299`.
   Сравнивать по `enum_id`, не по тексту. Читать значения —
   `amo_exchange.field_values(entity, field_id)` (см. как читается
   `AMO_FIELD_OWNER_HANDLES` в `notifications/client_messaging.py:356`).
6. Правило модуля `client_messaging.py`: решения — чистые функции без сети и
   базы, тонкий слой в `bot.py`. Соблюсти.
7. Лимиты и каналы очереди: `crm/wahelp_dispatcher.py` `send_with_rules` —
   ничего не менять, письмо идёт общим путём. Если у клиента нет канала,
   письмо упадёт как любое другое, и это видно в суточной сводке.

## Что сделать

### 1. `docs/notification_rules.json` — новое событие

```json
{"key": "order_cancelled_no_need",
 "name": "Отмена заказа: сделка закрыта с причиной «Пропала потребность»",
 "recipient": "client", "condition": null,
 "timing": {"delay_minutes": 0},
 "template": "Ваш заказ на {{date}} отменён. Если это ошибка или захотите записаться снова, просто свяжитесь удобным способом. Ваша raketaclean.ru",
 "variables": ["date"]}
```

Если правила читаются ещё и из `notification_rules.json.local` /
backup-файла — обновить только канонический файл, остальные не трогать
(исполнителю проверить, откуда читает прод: `NOTIFICATION_RULES_PATH`).

### 2. `order_confirmations` — отметка «об отмене сообщили»

Новая колонка `cancel_notified_at timestamptz` (в `ensure_client_messaging_schema`,
`bot.py:1035`, через `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`). Пишется в
момент постановки письма в очередь. Гарантия «одно письмо на сделку».

### 3. `notifications/client_messaging.py` — чистое решение

```python
AMO_STATUS_CLOSED_LOST = 143
AMO_FIELD_CLOSE_REASON = 19215
AMO_CLOSE_REASON_NO_NEED = 8299
CANCEL_LETTER_EVENT = "order_cancelled_no_need"

def should_notify_cancel(*, deal, row, now) -> tuple[bool, str]:
```

Возвращает «слать / не слать» и причину словами (для сводки). Слать, если
ВСЕ условия:

- `deal` есть и `status_id == 143`;
- в поле 19215 стоит `enum_id == 8299`;
- `row.cancel_notified_at` пусто;
- `row.client_id` не пусто (очередь шлёт только записям `clients`);
- `row.order_at` не старше суток назад от `now` (допущение агента: сделку,
  закрытую с этой причиной уже после дня работы, считаем бухгалтерией, а не
  отменой — письмо «заказ на вчера отменён» клиента только запутает).
  Владелец может изменить порог — вынести в константу `CANCEL_LETTER_MAX_AGE`.

Какую карточку проверять: `deal_id`, если есть; иначе `lead_id`. Проверять
обе не нужно: причину ставят на закрываемой сделке, а у лида без дочерней
сделки закрываемая — он сам.

### 4. Тонкий слой в `bot.py` — шаг прохода

В проходе разговора с клиентом, после существующей работы:

1. выбрать строки `order_confirmations`, где `cancel_notified_at IS NULL`,
   `client_id IS NOT NULL`, `order_at >= now() - interval '1 day'`
   (тот же порог, что в чистой функции — чтобы не ходить в амо по старью);
2. для каждой — `fetch_lead(deal_id or lead_id)`; 404 → пропустить;
   сетевая ошибка → пропустить до следующего прохода (не падать);
3. `should_notify_cancel(...)` → если слать:
   - `dry_run` → только счётчик `cancel_rehearsal`, ничего не писать;
   - иначе `enqueue_notification(event_key=CANCEL_LETTER_EVENT, client_id,
     payload={"date": ...})`, `UPDATE order_confirmations SET
     cancel_notified_at = NOW()`, и если `status = 'planned'` и письмо-вопрос
     ещё не ушло (`asked_sent_at IS NULL`, `outbox_id` есть) —
     `cancel_outbox_entry(...)` + `status = 'dropped'`;
   - запись в `amocrm_api_events` с `action = 'cancel_notified'` (как
     `question_dropped`) — для истории.
4. счётчики в суточную сводку (`build_client_messaging_daily_summary_text`,
   `bot.py:6243`): «отмен сообщено: N».

Владельцу отдельного сообщения не слать: он либо сам нажал кнопку, либо сам
закрыл сделку. Одно событие — одно сообщение.
