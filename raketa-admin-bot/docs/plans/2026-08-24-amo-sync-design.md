# Дизайн: админ-бот и автоматизация проведения сделок в amoCRM

Дата: 2026-08-24. Статус: **одобрен владельцем** (все секции согласованы в диалоге).
Основание: разведка `~/Projects/tgbot-v1/recon/` (00-summary, метрики M1–M9, процессы как есть).

## 1. Цель

Убрать ручное проведение сделок в amoCRM. Сегодня владелец руками: находит/заводит лида в первичной воронке, проводит в «Передано в работу», затем проводит автосделку в воронке реализации до «ЗАКАЗ ВЫПОЛНЕН и Оплата получена» (~2,5 сделки в день, плюс разбор недельных завалов после отпусков). Данные для всей цепочки уже есть в БД рабочего Telegram-бота.

## 2. Решения владельца (зафиксированы)

1. **v1 = полный цикл от данных бота**: заказ, закрытый мастером в боте → вся цепочка амо до финального этапа. Календарь — этап 2 (оперативность, отмены), ковры из Excel — этап 3 (достаточно раз в неделю, ~200–300 $/мес), замена CSV-импорта амо→бот — этап 4.
2. **Отдельный сервис («админ-бот»), не модуль прод-бота.** В будущем — платформа для административных функций владельца. Строить модульно, без хардкода, с разделением ядра и функций.
3. **Автономия**: однозначные случаи проводит сам; неоднозначные — карточка-вопрос владельцу в Telegram с кнопками.
4. **Режим**: проводить сразу после закрытия заказа мастером + вечерняя сверка в 21:00 со сводкой.
5. **Хвост**: при первом запуске разобрать все непроведённые заказы с 2026-08-21 (пятница) — это же боевой тест.
6. **Автозадачи амо** («Назначь мастера», «Выполни заказ» и пр.) закрывать при проведении сделки.
7. **Поле «Услуга»**: если заполнено — не трогать; если пусто/новая сделка — по мастеру заказа: Никита или Дима → «мебель», Оля → «клининг» (точные enum-значения списка амо подобрать при реализации). После подключения календаря услугу брать оттуда.
8. **Бюджет сделки** = полная сумма чека из бота (включая доп. продажу).
9. Задача **«Получить ОС»**: если клиент уже поставил оценку боту — закрывать; если нет — оставлять владельцу (он «последняя инстанция»).
10. Имя проекта: **raketa-admin-bot**.

## 3. Архитектура

Новый репозиторий `raketa-admin-bot`, новый systemd-сервис на том же VPS (91.200.150.68), по образцу деплоя аналитики (`tgbot-v1/docs/analytics_deploy.md`).

```
raketa-admin-bot
├─ Ядро (переиспользуется всеми будущими функциями)
│   ├─ Telegram-интерфейс: отдельный бот (токен из BotFather), только владелец;
│   │   отчёты, карточки-вопросы с inline-кнопками, команды управления
│   ├─ Доступ к БД рабочего бота: ТОЛЬКО ЧТЕНИЕ (orders, order_masters, staff,
│   │   clients, rating-поля)
│   ├─ Собственное хранилище: отдельная схема в том же Postgres
│   │   (привязки заказ→сделка, чек-листы шагов, очередь вопросов, курсоры)
│   └─ Конфиг (.env) + выключатель на каждую функцию
└─ Функция amo_sync (v1)
    ├─ Наблюдатель: poll БД бота ~раз в минуту; «новый» = заказ без привязки
    ├─ Матчер («сваха»): канонический посимвольный парсер телефона (порт из
    │   bot.py:3251) + правила: приоритет воронки реализации, дата ±2 дня,
    │   взаимное распределение пар «два заказа — две сделки»
    ├─ Исполнитель: клиент amoCRM API v4 (чтение + запись) — заполнение полей,
    │   смена этапов, создание сделок/контактов, закрытие задач
    └─ Вечерняя сверка 21:00 МСК + сводка в Telegram
```

Граничные правила:
- В таблицы рабочего бота не пишем никогда.
- В амо пишем через НОВУЮ интеграцию с правом записи (создаёт владелец; в истории сделок видно, что действовал робот).
- Каждая функция включается/выключается независимо; «⏸ Стоп» из Telegram.

## 4. Путь заказа (пути А–Г)

- **А. Есть автосделка в воронке реализации** → заполнить бюджет, провести в 142 («ЗАКАЗ ВЫПОЛНЕН и Оплата получена»), закрыть автозадачи.
- **Б. Есть только лид в первичной воронке** → заполнить (Услуга, «Дата и время заказа», Адрес, бюджет) → «Передано в работу» → ждать автосделку сейлзбота (до 10 мин) → путь А.
- **В. Сделки нет** (~1/нед) → найти/создать контакт по телефону → создать сделку в первичной воронке → путь Б. Если заказ есть в боте — это гарантированно НЕ ковры (ковры идут только через Excel партнёра).
- **Г. Несколько кандидатов, правила не решили** → карточка-вопрос владельцу («заказ №…, кандидаты…, [та][эта][создать новую]»); заказ ждёт; вечерняя сверка напоминает.
- Обратная связь: оценка в БД бота есть → закрыть задачу «Получить ОС»; нет → оставить.
- Отчётность: днём тихо (кроме карточек-вопросов), в 21:00 сводка: проведено/создано/ждут ответа.

## 5. Надёжность

1. Сделка уже на финальном этапе (провели руками) → только привязать, не трогать.
2. Амо недоступно/токен протух → ретраи с паузами; заказы копятся в очереди; после 30 мин молчания — алерт владельцу; после восстановления очередь разгребается.
3. Автосделка сейлзбота не появилась за 10 мин → карточка-вопрос.
4. Идемпотентность: каждый шаг по сделке фиксируется чек-листом в своём хранилище; повторный запуск продолжает с места остановки, дублей не создаёт.
5. Аварийный выключатель из Telegram: «⏸» — копим, не пишем; «▶️» — разгребаем.
6. Прозрачность: отдельное имя интеграции в истории сделок амо.

## 6. Проверка качества и запуск

1. **Экзамен на истории**: прогнать матчер по 90 дням (171 заказ ↔ реально проведённые сделки) в режиме чтения; сверить решения с фактическими действиями владельца; целевые метрики из разведки: ≥92% авто, ≤8% вопросов.
2. **Автотесты**: все хитрые кейсы разведки (пары заказов, протухшие даты, B2B-клиент с 33 сделками) — постоянные регрессионные тесты.
3. **Репетиция на VPS**: режим «решаю, но не пишу», 1–2 дня, решения шлются владельцу.
4. **Боевой старт**: хвост с 21.08 — предпросмотр плана в Telegram → кнопка «Поехали» → запись. Затем обычный режим + неделя наблюдения.

От владельца при внедрении: токен бота из BotFather; интеграция амо с правом записи.
